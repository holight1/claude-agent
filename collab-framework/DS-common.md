# DS-common.md — AI 协作通用规则

本文件由架构师统一维护，适用所有仓库。各仓库 DS.md 顶部引用本文件。

---

## 上下文隔离（硬性规则）

每次收到新任务时，完全放弃之前任务的上下文和工作记忆。
每个任务是独立的，不引用、不混入之前任务的代码或结论。

---

## 工作流程

1. 读取本仓库 `DS.md`（项目 context）
2. 读取 `CLAUDE.md`（如存在，有构建/测试命令和项目规则）
3. 读取任务相关知识库章节（`code-agent/knowledge/README.md` 有索引）
4. 读取并执行任务文件
5. 在任务文件末尾 `## 完成区` 填写结果，更新顶部 `**状态**` 为 `已完成`
6. 按需更新知识库，在 `10-changelog.md` 追加一行记录

---

## 完成区规范

```markdown
## 完成区

**状态**：已完成 / 部分完成 / 失败
**修改文件**：
**验收结果**：
**遗留问题**：
```

项目可在 DS.md 中扩展此格式（如加 Codex Review section）。

### 完成标准（硬性规则）

**任务文件 `## 验收条件` 里的每一条必须全部通过，才能把状态标为 `已完成`。**

- 有任何一条未通过 → 状态标 `部分完成`，继续推进，不能直接返回
- 推进后仍无法通过 → 状态标 `失败`，在完成区明确写出：卡在哪条验收、现象是什么、已尝试方案
- **`遗留问题` 只记录"验收已通过、但本任务范围之外"的后续事项**；验收未通过的条目不属于遗留，必须继续处理

## 验收准则（强制）

### 1. 测试断言不可降级

任务文件中列出的断言是**功能验收门控**，不是参考写法。以下操作**严禁**：

| 严禁操作 | 示例 |
|---------|------|
| 把硬断言改成 info 打印 | `EXPECT_GT(hits, 0)` → `fprintf(stderr, ...)` |
| 放宽阈值让测试通过 | `EXPECT_LE(mismatch, 2)` → `EXPECT_LE(mismatch, 32)` |
| 删除断言 | 注释掉 `EXPECT_GT` |
| 把 PASS 断言改成 FAIL 断言 | `EXPECT_GT(hits, 0)` → `EXPECT_EQ(hits, 0)` |

**测试失败 → 修实现，不是修断言。**

### 2. 遇到测试失败的正确流程

```
实测失败 → 调查根因 → 根因在范围内：修实现 → 重跑
                     → 根因超出范围：完成区写 ❌ + 根因 → 等待架构师指示
```

### 3. 完成区如实填写

- 数据来自实际运行输出，不得估算或复制任务文件的预期值
- 未达成时写：`❌ 未达成，实测：[值]，根因：[一句话]`
- 不得把断言降级后在完成区写 ✅

### 4. 测试文件改动范围

- 只改任务文件明确列出的测试改动
- 不得"顺带"修改未在任务中提及的断言或阈值

### 5. 验收对象不可偷换（防 gate-gaming）

**验收命令必须真实 exercise 任务要测的那个对象**，不得为"过门槛"而偷换或缩小被测对象：

| 严禁 | 例 |
|------|----|
| 用手搓/旁路产物替代真实被测系统 | 手写一个能过命令的结果，绕过本该被测的工具/流程 |
| 缩小到不触发问题的更简单情形 | 任务要测 A+B 交互，只测 A 让命令通过 |
| 让命令"绿"但没测到目标 | 退出码/输出对了，但来源不是任务要验证的路径 |

真实对象跑不通 → 完成区写 `❌ + 卡在哪层 + 根因`，**等架构师指示；绝不手搓替代冒充完成**。门槛是用来暴露"没做到"的，不是用来"想办法弄绿"的。

### 6. 测试必须真的约束它声称的性质（第三类失败）

前两类失败是**断言被降级**和**验收对象被偷换**。还有第三类，最常被漏掉：

> **断言在、没降级、验收对象也没换，但断言与用例名/注释声称的性质无关。**

判据是**反例证伪法**：

> **把实现换成一个明显错误的版本，这条测试会不会失败？**
> **不会 ⇒ 它没有在守护它声称的性质。**

不必真改源码，写几行临时脚本用坏实现跑一遍断言逻辑即可。**优先对这几类用例做**：

- 名字里含 stable / unique / independent / deterministic / isolated / distinct 的
- 声称「新增 X 不影响 Y」的 → 坏实现：让 X 与 Y 共用同一状态
- 声称「A 与 B 不同」的 → 坏实现：让 A 与 B 返回同一个东西
- 只断言了「两次调用一致」，却声称测了「不同输入产生不同结果」的

**反向也查**：对每条验收点问「实现若写错，现有哪条用例会红」——答不上来就是缺口。**缺失的测试和写坏的测试一样重要。**

自审时对新增/修改的测试各做一遍，结论写进完成区；做过反例证伪的，**贴出坏实现下测试变红的实际输出**。

### 7. 数值常量：参数、门限、系数一视同仁

任何**无出处的数值**都要有出处，不因为"它不是参数"就放过。

- **参数**（带宽、容量、超时、路径…）→ 来自配置或规格文件，不得硬编码进逻辑
- **门限与系数**（形如 `if x > y * 1.5` 的判定常数）→ 同样要出处。"看起来合理"不是出处
- **可内嵌的例外**：单位换算、物理耦合比可以内嵌，但**必须带出处注释**并在完成区披露

⚠️ 防魔数检查自身带一份常量清单时，**先审那份清单全不全**。清单不全 ⇒ 实现、测试、审查三方会一起对着残缺规格"全部正确"。

## 禁止事项

- **不 push**，任何情况下都不向远端推送
- 不填写「Codex review 通过」「架构师已确认」这类**不属于你的结论**
- 不修改任务文件未列出的文件
- **不得为「解锁」当前任务而删除 / 破坏之前已工作的文件、hook 或公共路径**（= 回归；确需改动先在完成区写明理由，别静默删）
- 不改变已有函数签名（除非明确要求）
- 不引入新的外部依赖（除非明确要求）

## git commit 边界

**你可以为单个任务在本地 commit**（代码 + 任务文件的完成区），但：

| 允许 | 禁止 |
|---|---|
| 本地 commit，一个任务一个 commit | **push**（任何情况） |
| commit message 写清任务号与实际改了什么 | 合并、rebase、reset 已有历史 |
| 在完成区注明 commit 的短 SHA | 在 message 或完成区写 review 结论 |

**为什么允许**：commit 是 review 的**边界**。没有它，架构师在工作树里看到的是一堆混在一起的改动，分不清哪些属于本任务——一个任务的产出必须能被单独指认，才能被单独复跑和单独打回。

**为什么仍然不 push**：push 是对外副作用，需要用户明确授权。架构师复跑通过后由架构师决定。

**commit 不等于通过。** 你的 commit 只是把改动**装箱**，不代表验收结论。架构师会在你的 commit 之上独立复跑；结论以复跑为准，与你是否 commit 无关。

## 安全清理规则（硬性，防 code-agent 被误删）

**背景**：`code-agent/` 目录（tasks/、knowledge/、designs/）里存储调研产出、任务文件、跨仓契约文档，是架构师和 DS 的共享工作区。**这些文件在架构师 commit 之前长期以 untracked 状态存在**，任何无差别的 "清理 untracked 文件" 操作都会造成灾难性数据丢失。

### 严禁使用的命令

以下命令**绝对禁止**，无论出于什么目的：

| 命令 | 危害 |
|------|------|
| `git clean -xfd` / `-xff` / `-fdX` | 递归删除 untracked 文件和目录，**会杀掉整个 code-agent/**（含所有调研产出） |
| `git clean -fd` | 同上（少 -x 但仍杀 untracked） |
| 任何 `git clean` 加 `-d` / `-f` / `-x` 组合 | 见上 |
| `rm -rf` 未在任务文件明确列出的目录 | 潜在杀伤面无边界 |
| `rm -rf $(pwd)` / `rm -rf .` / `rm -rf *` | 灾难性 |
| `find . -delete` / `find . -exec rm` 无 filter | 同上 |

### 安全清理的正确做法

需要清理 build 产物或临时文件时，用**明确白名单**：

```bash
# 正确：只清指定目录 / 后缀
make distclean                          # 用工程自带的清理 target
make clean
rm -rf build/                           # 只清 build/
rm -rf /tmp/mywork/                     # 只清自己的临时目录
find . -maxdepth 2 -name "*.o" -delete  # 明确后缀，限制深度

# 需要用 git clean 时，先 dry-run + 白名单 pathspec
git clean -nd -- build/ output/         # -n 是 dry-run，先看要删什么
git clean -fd -- build/ output/         # 白名单，且不加 -x
```

**核心规则**：任何清理命令执行前，**必须问自己："这条命令会不会碰到 code-agent/ 目录？"** 只要不能百分百确定不碰，就换更保守的写法。

### 出事怎么办

若不慎误删 code-agent/：

1. **不要**立刻做任何 git 操作（可能覆盖 reflog）
2. **立刻在完成区写下事故报告**：什么命令、什么时机、丢了哪些文件、能不能从对话上下文重建
3. 尝试从 shell history、任务文件、对话上下文重建产物
4. 状态标 `部分完成` 或 `失败`（视重建情况），**不得**掩盖事故当作"已完成"

## 遇到问题的查询顺序

1. **先查知识库** `code-agent/knowledge/`（README.md 有索引）
   - 有答案直接采用，不另行搜索代码"验证"
2. **知识库未覆盖时**再查源码，只读取直接相关文件
3. **禁止**跳过知识库直接 `grep -r` / `find` 全库扫描

## 阻塞处理

遇到 blocker 时：明确报告现象和已尝试方案，不静默失败。
若任务标注"不做完不返回"：记录阻塞到进度文件，继续推进其余部分，全部完成或均阻塞后再返回。
