## 上下文隔离（硬性规则）

每次收到新任务时，完全放弃之前任务的上下文和工作记忆。
每个任务是独立的，不引用、不混入之前任务的代码或结论。

## 工作流程

1. 读取本仓库 `DS.md`（项目 context）
2. 读取 `CLAUDE.md`（如存在，有构建/测试命令和项目规则）
3. 读取任务相关知识库章节（`code-agent/knowledge/README.md` 有索引）
4. 读取并执行任务文件

   ⚠️ **公式 / 换算 / 推导类实现：先手算，再写代码。** 当规格同时给出**推导过程**（伪码、公式）和**权威结果数字**（表格里的量）时，权威数字是唯一真值。**实现前先用它手算一遍验证方向**，实现中对照手算值。

   否则顺序就反了——先按伪码直写、再拿权威数字当测试期望值兜底。方向错的实现会一直错到测试才被撞回来，而伪码的口径歧义（「每条目」还是「每 token」）在手算时一眼可见、在代码里看不出来。

   这与「审查不能只依赖任务书」同源：**权威数字是任务书之外的独立 oracle**，照伪码直写等于只用了一个 oracle。

5. 在任务文件末尾 `## 完成区` 填写结果，更新顶部 `**状态**` 为 `已完成`
6. 按需更新知识库，在 `10-changelog.md` 追加一行记录

## 完成区规范

```markdown
## 完成区

**状态**：已完成 / 部分完成 / 失败
**修改文件**：
**验收结果**：
**遗留问题**：
```

### 整改记录（对 reviewer 意见的处理）

🔴 **整改是独立小节，不是完成区末尾的一段话。** 每条整改必须三段式：

1. **reviewer 意见原文**（可截断）
2. **做了什么**
3. **证据命令与输出**——`git diff --stat`、`grep -n`、测试输出

**纯文字类整改同样要贴证据。** 改完成区、改文档措辞、撤下清单里的一行，都要贴 `grep -n` 的**改后**结果——这类恰恰是最容易只写不做的：在只需要动一行字的动作上，决定与执行之间的距离短到人会以为自己已经做了。

🔴 **声称「撤下 / 删除 / 改名」的动作，证据必须是「查不到」，不是「我改了」。** 贴 `grep -c` 为 0，或 diff 里的删除行。

> 实测事故：整改记录写「完成区文件清单**撤下** `hierarchy.py`」，而 `grep -n` 显示原清单行原封不动还在（只多了一行「已撤下」的自述）。同一条记录的另一项是真做了的 —— 所以问题不是整体敷衍，是**单条落空**，因此必须逐条附证据，不能因为一条是真的就放过整段。

### 完成标准（硬性规则）

**任务文件 `## 验收条件` 里的每一条必须全部通过，才能把状态标为 `已完成`。**

- 有任何一条未通过 → 状态标 `部分完成`，继续推进，不能直接返回
- 推进后仍无法通过 → 状态标 `失败`，在完成区明确写出：卡在哪条验收、现象是什么、已尝试方案
- **`遗留问题` 只记录"验收已通过、但本任务范围之外"的后续事项**；验收未通过的条目不属于遗留，必须继续处理

## 验收准则（强制）

### 1. 测试断言不可降级

任务文件中列出的断言是**功能验收门控**，不是参考写法。以下操作**严禁**：

| 严禁操作 | 示例 |
|---------|------|
| 把硬断言改成 info 打印 | `EXPECT_GT(hits, 0)` → `fprintf(stderr, ...)` |
| 放宽阈值让测试通过 | `EXPECT_LE(mismatch, 2)` → `EXPECT_LE(mismatch, 32)` |
| 删除断言 | 注释掉 `EXPECT_GT` |
| 把 PASS 断言改成 FAIL 断言 | `EXPECT_GT(hits, 0)` → `EXPECT_EQ(hits, 0)` |

**测试失败 → 修实现，不是修断言。**

### 2. 遇到测试失败的正确流程

```
实测失败 → 调查根因 → 根因在范围内：修实现 → 重跑
                     → 根因超出范围：完成区写 ❌ + 根因 → 等待架构师指示
```

### 3. 完成区如实填写

- 数据来自实际运行输出，不得估算或复制任务文件的预期值
- 未达成时写：`❌ 未达成，实测：[值]，根因：[一句话]`
- 不得把断言降级后在完成区写 ✅

### 4. 测试文件改动范围

- 只改任务文件明确列出的测试改动
- 不得"顺带"修改未在任务中提及的断言或阈值

#### 验收对象不可偷换

**验收命令必须真实 exercise 任务要测的那个对象**，不得为"过门槛"而偷换或缩小被测对象：

| 严禁 | 例 |
|---|---|
| 用手搓/旁路产物替代真实被测系统 | 手写一个能过命令的结果，绕过本该被测的工具/流程 |
| 缩小到不触发问题的更简单情形 | 任务要测 A+B 交互，只测 A 让命令通过 |
| 让命令"绿"但没测到目标 | 退出码/输出对了，但来源不是任务要验证的路径 |
| **同一份代码，但调用方与实现的单位/时基口径不一致** | 差几个数量级而两侧各自自洽。**这是无意的偷换**，写测试的人自己不知道 |

**量纲以被调用者的签名/规格为准，不得以调用点的注释为准。** 照注释核量纲会得到一个自洽的错误答案——它比不核更危险，因为它留下了「已核对」的痕迹。

**负测试的数字必须能用交付实现的签名复算出来。复算差整数个数量级 ⇒ 它跑的不是交付物。**

#### 一条绿色结果成立的四个条件

1. **退出码取自被验证的那条命令**——避免管道，或用 `${PIPESTATUS[0]}`；`cmd | tail; echo $?` 取到的是 `tail` 的
2. **处理单元数不为 0**——校验工具要打印它处理了多少单元；**0 个 = 该验证无效**，不是通过
3. **作用于真实交付入口**——流程里若有 restore / reset / fixture 重建，被测对象可能在跑之前已被治好
4. **被约束量的量级落在断言的作用域里**——问：*这个数离断言的界有多远？* 差整数个数量级 ⇒ **该断言无信息量**，通过不构成证据

对每条绿色结果问一次：**如果实现是错的，这条命令会不会红？** 答不上来 ⇒ 它不构成证据。

不是「我改了」。要贴 `grep -c` 为 0，或 diff 里的删除行。

#### 测试强度：三类失败，缺一类就漏

| # | 失败形态 | 怎么查 |
|---|---|---|
| 1 | **断言被降级** | 改成打印、放宽阈值、删除断言、期望值改成实际值、跳过/预期失败标记 |
| 2 | **验收对象被偷换** | 手搓产物替代真实被测系统；缩小到不触发问题的更简单情形；命令"绿"了但没走到目标路径 |
| 3 | 🔴 **通过但不约束它声称的性质** | 断言在、没降级、对象没换，**但断言与用例名/注释声称的性质无关** |

**第三类的判据是反例证伪法**：

> **把实现换成一个明显错误的版本，该测试会不会失败？不会 ⇒ 它没在守护它声称的性质。**

不必真改源码，写几行临时脚本用坏实现跑一遍断言逻辑即可。**优先对这几类做**：名字含 stable / unique / independent / deterministic / distinct 的；声称「新增 X 不影响 Y」的（坏实现让两者共用状态）；声称「A 与 B 不同」的（坏实现让两者返回同一个东西）；只断言「两次调用一致」却声称测了「不同输入产生不同结果」的。

**反向也查**：对每条验收点问「实现若写错，现有哪条用例会红」——答不上来就是缺口。**缺失的测试和写坏的测试一样重要。**

做过反例证伪的，**贴出坏实现下测试变红的实际输出**。

#### 数值常量：参数、门限、系数一视同仁

任何**无出处的数值**都要有出处，不因为"它不是参数"就放过。

- **参数**（带宽、容量、超时、路径…）→ 来自配置或规格文件，不得硬编码进逻辑
- **门限与系数**（形如 `if x > y * 1.5` 的判定常数）→ 同样要出处。"看起来合理"不是出处
- **可内嵌的例外**：单位换算、物理耦合比可以内嵌，但**必须带出处注释**并在完成区披露

⚠️ **防造假机制 = 规则 + 作用集合。** 集合比规则更容易悄悄缩小：先审那份清单/扫描集全不全，特别是**推导得出的值**（不在数据文件里，最容易被自动生成的集合绕开）和**集合从手工列举改成自动生成之后**（边界变得不可见）。

自审时对新增/修改的测试各做一遍第三类检查，结论写进完成区。

#### 引文

- 引文必须是原文**连续**的一段。非连续原文**不得缝成一条**
- 转述时原样保留：**行为者、条件、时序、情态（may / 建议 / 预计）、否定保证、例外**
- 注意这句话在原文里是**论据、反例、还是被否的提案**——身份搞反比引错字更难发现
- 拿不准就**给原文，不只给转述**

#### 数字

- 每个数字**附产生它的命令**。预期值、文档记载值、口述值都不是实测值
- 写下之前问：这个数统计的**单元**是什么？有没有把译文、别名、重复项算进去？
- 「我用脚本核过了」不等于「脚本核的是这个对象」——先看它处理了几个单元

#### 报告

分开写，不许混：**我核对到不对**（有出处与原文）／**我认为不合适**（判断，无实据）／**我无法核对**（必填：哪些材料不在手里、哪些结论只能存疑）。

「无法核对」空着，会让「通过」被读成全面核对过。

写任何**自动判定通过/不通过**的东西时（测试、校验脚本、格式检查、防魔数清单）：

#### 1. 先定义作用集合，再写规则

门禁 = **一条规则 + 它作用的对象集合**。集合才是最容易悄悄缩小的地方。

**收敛判据**：

> **新增一个此前没有的同类对象时，它是自动落入守护范围，还是需要有人记得去加？需要人记得 ⇒ 边界没定义好。**

#### 2. 同类缺口第二次换位置：换修法

| 第几次 | 处置 |
|---|---|
| 第一次 | 正常修 |
| **第二次换位置** | **禁止再用「扩大覆盖」修法**，必须写出能对任意新对象回答「它该不该被守护」的**判别式** |
| **第三次** | 视为设计债，单开任务偿还 |

#### 3. 单向断言从两侧夹住被约束量

`x <= B` / `x >= B` 只在越界时说话，**「量永远远离界」与「量被机制拦在界处」在它看来一样**，前者是空转。

- `x <= B` 另配 `x >= k·B`（`0<k<1`）；`x >= B` 另配 `x <= B/k`。给 `x >= B` 补 `x >= 0.5B` 是**恒真式**
- 让量走到 `k·B` 的**构造参数必须由 `B` 推出**，不得写死；否则界一变，测试红在错的地方、报错还指错方向
- **只对声称「某机制把量拦在界内」的断言强制**（clamp / 饱和 / 限速 / 配额）。纯不变量该有大余量 ⇒ 别逼它逼近界，另写对抗构造去顶界
- 报告给**比值**，不只写「通过」——只写通过时，空转与真守护打出的字一样

判据：**把被约束量改成永远不接近界的值，这条断言会不会红？** ⚠️ 它与「坏实现会不会红」是两问：后者预设实现有错，而空转常发生在实现正确时。

#### 4. 其余五条

- **打印处理单元数**，0 个不得成功
- **每条接受路径都要有会失败的无效输入**；做不到的那条不构成检查
- **校验最终状态**，不把「运行过命令」当成「状态已成立」——创建/写入后回读再计数
- **被跳过的对象要能列出来**，不能只报数量
- **判别式自身的输入写错时必须显式失败**，不得静默跳过——否则守护集合可以静默变空而全部测试仍绿

## git commit 边界

**你可以为单个任务在本地 commit**（代码 + 任务文件的完成区），但：

| 允许 | 禁止 |
|---|---|
| 本地 commit，一个任务一个 commit | **push**（任何情况） |
| commit message 写清任务号与实际改了什么 | 合并、rebase、reset 已有历史 |
| 在完成区注明 commit 的短 SHA | 在 message 或完成区写 review 结论 |

**为什么允许**：commit 是 review 的**边界**。没有它，架构师在工作树里看到的是一堆混在一起的改动，分不清哪些属于本任务——一个任务的产出必须能被单独指认，才能被单独复跑和单独打回。

**为什么仍然不 push**：push 是对外副作用，需要用户明确授权。架构师复跑通过后由架构师决定。

**commit 不等于通过。** 你的 commit 只是把改动**装箱**，不代表验收结论。架构师会在你的 commit 之上独立复跑；结论以复跑为准，与你是否 commit 无关。

## 安全清理规则（硬性，防 code-agent 被误删）

**背景**：`code-agent/` 目录（tasks/、knowledge/、designs/）里存储调研产出、任务文件、跨仓契约文档，是架构师和 DS 的共享工作区。**这些文件在架构师 commit 之前长期以 untracked 状态存在**，任何无差别的 "清理 untracked 文件" 操作都会造成灾难性数据丢失。

### 严禁使用的命令

以下命令**绝对禁止**，无论出于什么目的：

| 命令 | 危害 |
|------|------|
| `git clean -xfd` / `-xff` / `-fdX` | 递归删除 untracked 文件和目录，**会杀掉整个 code-agent/**（含所有调研产出） |
| `git clean -fd` | 同上（少 -x 但仍杀 untracked） |
| 任何 `git clean` 加 `-d` / `-f` / `-x` 组合 | 见上 |
| `rm -rf` 未在任务文件明确列出的目录 | 潜在杀伤面无边界 |
| `rm -rf $(pwd)` / `rm -rf .` / `rm -rf *` | 灾难性 |
| `find . -delete` / `find . -exec rm` 无 filter | 同上 |

### 安全清理的正确做法

需要清理 build 产物或临时文件时，用**明确白名单**：

```bash
# 正确：只清指定目录 / 后缀
make distclean                          # 用工程自带的清理 target
make clean
rm -rf build/                           # 只清 build/
rm -rf /tmp/mywork/                     # 只清自己的临时目录
find . -maxdepth 2 -name "*.o" -delete  # 明确后缀，限制深度

# 需要用 git clean 时，先 dry-run + 白名单 pathspec
git clean -nd -- build/ output/         # -n 是 dry-run，先看要删什么
git clean -fd -- build/ output/         # 白名单，且不加 -x
```

**核心规则**：任何清理命令执行前，**必须问自己："这条命令会不会碰到 code-agent/ 目录？"** 只要不能百分百确定不碰，就换更保守的写法。

### 出事怎么办

若不慎误删 code-agent/：

1. **不要**立刻做任何 git 操作（可能覆盖 reflog）
2. **立刻在完成区写下事故报告**：什么命令、什么时机、丢了哪些文件、能不能从对话上下文重建
3. 尝试从 shell history、任务文件、对话上下文重建产物
4. 状态标 `部分完成` 或 `失败`（视重建情况），**不得**掩盖事故当作"已完成"

## 流程缺口 vs 实现缺陷

发现的问题若属于**流程允许它发生**（清单缺一类、任务书写得不充分、审查漏掉一整类），写进 `code-agent/process-notes/`，**不要与任务终审区混写**——终审区写这次的判决，process-notes 写下次怎么不再发生。

判据：**同一个人下次做同一件事，会不会再犯？** 会 ⇒ 是流程缺口。单纯的实现 bug、笔误写在完成区就够了。

制度见 skill `process-gap-capture`。

## 遇到问题的查询顺序

1. **先查知识库** `code-agent/knowledge/`（README.md 有索引）
   - 有答案直接采用，不另行搜索代码"验证"
2. **知识库未覆盖时**再查源码，只读取直接相关文件
3. **禁止**跳过知识库直接 `grep -r` / `find` 全库扫描

## 阻塞处理

遇到 blocker 时：明确报告现象和已尝试方案，不静默失败。
若任务标注"不做完不返回"：记录阻塞到进度文件，继续推进其余部分，全部完成或均阻塞后再返回。
