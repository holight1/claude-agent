## 审查重点

| 类型 | 检查什么 |
|------|---------|
| 验收断言 | 是否覆盖任务要求？是否被降级（放宽阈值、改为 info 打印、删除）？ |
| 实现路径 | 是否真正命中了任务要求的执行路径，而不是绕路通过？ |
| 完成区诚实性 | 数据是否来自实际运行？与任务要求的预期值是否一致？ |
| 边界安全 | 空指针/越界/资源泄漏 |
| 测试强度 | 见下方三类失败表 |
| 数值常量 | 参数、门限、系数是否都有出处 |
| 合同盲区 | 本次审查有没有一部分不依赖任务书 |

### 测试强度：三类失败，缺一类就漏

| # | 失败形态 | 怎么查 |
|---|---|---|
| 1 | **断言被降级** | 改成打印、放宽阈值、删除断言、期望值改成实际值、skip / 预期失败标记 |
| 2 | **验收对象被偷换** | 手搓产物替代真实被测系统；缩小到不触发问题的更简单情形；命令"绿"了但没走到目标路径 |
| 3 | 🔴 **通过但不约束它声称的性质** | 断言在、没降级、对象没换，**但断言与用例名/注释声称的性质无关** |

第三类的判据是**反例证伪法**：

> **把实现换成一个明显错误的版本，这条测试会不会失败？不会 ⇒ 它没在守护它声称的性质。**

不必真改源码，写几行临时脚本用坏实现跑一遍断言逻辑即可。**优先对这几类做**：名字含 stable / unique / independent / deterministic / distinct 的；声称「新增 X 不影响 Y」的（坏实现让两者共用状态）；声称「A 与 B 不同」的（坏实现让两者返回同一个东西）。

**反向也查**：对每条验收点问「实现若写错，现有哪条用例会红」——答不上来就是缺口。

### 数值常量：参数、门限、系数一视同仁

任何**无出处的数值**都要问出处。参数来自配置或规格；门限与系数（`if x > y * 1.5` 这类）同样要出处，"看起来合理"不是出处；单位换算与物理常数可内嵌，但必须带出处注释并在完成区披露。

⚠️ 防魔数检查自身带常量清单时，**先审那份清单全不全**。清单不全 ⇒ 实现、测试、审查三方一起对着残缺规格"全部正确"。

### 合同盲区

**以任务书为唯一判据的审查，原理上抓不到任务书本身的缺陷。** 每次审查**至少留一部分不依赖任务书**：挑 2–3 个关键数值或算法自己独立算一遍，与实现输出对照——不是"对着验收表打勾"。

> 上面三节的来由与原始证据：`~/claude-agent/decisions/2026-08-21-contract-blindspot.md`、`~/claude-agent/decisions/2026-08-21-project-to-framework-backflow.md`

**断言降级是最高优先级阻断**。DS 常见的降级手段：
- `EXPECT_GT(hits, 0)` → `fprintf(stderr, ...)`（软化为打印）
- `EXPECT_LE(mismatch, 2)` → `EXPECT_LE(mismatch, 32)`（放宽阈值）
- 直接删除断言或注释掉 EXPECT_*
