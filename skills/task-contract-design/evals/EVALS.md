# task-contract-design · eval

## 正触发

| 场景 | 期望 |
|---|---|
| 创建任务文件与验收条件 | 触发；四栏映射 + 作弊搜索 |
| 大改已有任务的验收条件 | 触发 |
| 把模糊需求变成可下发的合同 | 触发；先确认能否机械验收 |

## 负触发

| 场景 | 为什么不该触发 |
|---|---|
| 改任务文件的错别字或路径 | 不改变约束 |
| 填写完成区 | 那是执行端的动作 |
| 决定这个任务发给谁 | 那是 `worker-routing-and-delegation` |

## 诱人错误

| 场景 | 省力但错误的判断 | 本 skill 应给出的判断 | 判据 |
|---|---|---|---|
| 验收表写「811 / 768 / 1152 / 202.75 **…**」 | 清单已给出，够明确 | 省略号 = 不完整清单，而**不完整看起来和完整一模一样**；实现、测试、审查会一起对着残缺规格「全部正确」 | 判据：§2. 作弊搜索 |
| 验收点写「扫描集自动生成」 | 机制已规定，可验收 | 只写了**怎么做**，没写**做到什么程度算够**；生成源的选择权在执行端手里，它会选最省事的那个 | 判据：§1. 每项主张映射到四样 |
| 四栏都填满了 | 这条验收条件写完了 | 四栏填满不等于有约束力；还要问「最省力的执行端能给出的最弱实现是什么，可接受吗」 | 判据：§1. 每项主张映射到四样 |
| 执行端精确满足了字面但意图落空 | 执行端不老实 | 实测本地 DS 不多不少满足字面、不造假 ⇒ **漏洞是任务设计的** | 判据：§要防的诱人错误 |
| 完成区写「测试全部通过」 | 可采信 | 每个数字必须附产生它的命令；预期值、文档记载值、口述值都不是实测值 | 判据：§3. 数字必须带命令 |
| 验收点写「credit 始终在 ±8192 内」，负测试写「去掉钳位必须红」 | 机制 + 程度都写了，够强 | 程度只写了**上界**没写下界 ⇒ 被约束量永远远小于界时断言一样绿。要同时要求「正常构造下逼近界」并贴比值 | 判据：§2. 作弊搜索 |
| 任务「流程」一行写「完成后自起 reviewer，架构师终审留空」 | 流程已交代清楚 | 没交代**整改**的产出格式；整改不是流程节点，是完成区末尾一段散文，会出现「写了没做」 | 判据：§5. 声明执行环境、写入策略与整改格式 |
