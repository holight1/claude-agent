# 任务合同设计

**状态**：enabled
**消费者**：架构师（CC）
**来源**：本框架任务设计实践 + dsh「门禁需要自己的负测试」原则
**核心判断**：这条验收条件，作弊是不是比做对更难？

## 何时用

**触发**：创建任务文件；大改验收条件；把一个模糊需求变成可下发的合同。

**不触发**：修改任务文件的错别字或路径；补充完成区。

## 要防的诱人错误

| 诱人错误 | 它为什么看起来对 | 代价 |
|---|---|---|
| 门槛写松，指望执行端补 | 执行端很聪明，应该会想到 | **实测：本地 DS 精确满足字面，不多不少**——它不补你的漏洞，但也不造假。漏洞是任务设计的，不是执行端的 |
| 用伪码 / 行号 / 手把手步骤说清楚 | 这样最不容易被误解 | 架构决策没被表达，执行端照抄；而且需要伪码才说得清，往往是自己还没想清 |
| meta 纪律堆满任务正文 | 防造假很重要，多写几遍更保险 | **稀释目标**，并诱导执行端去满足门槛字面而丢掉意图（gate-gaming） |
| 验收条件写成期望而非可核对项 | 「实现正确」「测试充分」读起来没毛病 | 只能靠信任验收；没有负测试就分不清「做对了」和「没跑到」 |
| 忘了声明执行环境与写入策略 | 上一个任务是在那个仓做的 | 路由错、或在上游 clone 里产生了不该有的 commit |

## 判断程序

### 0. 先确认这个任务能被机械验收

如果验收只能靠"读完成区觉得可信"，先回到 `worker-routing-and-delegation` 换 worker，而不是把任务写得更详细。

**门槛的强度上限 = 写任务时的思考深度。** 写任务时想不清的地方，验收时也核不出来。

### 1. 每项主张映射到四样

| 主张 | 真实对象 | 可观察结果 | 处理单元数 | 负测试 |
|---|---|---|---|---|

四栏有空的，那一条就还不是验收条件。

### 2. 作弊搜索（本 skill 的核心）

对每条验收条件问：**最省力地把它弄绿的办法是什么？** 把答案写出来，然后堵掉。

已知的省力路径，写禁令时**点名具体手法，不写抽象原则**：

- 缩小到不触发问题的更简单情形
- 走旁路入口，不走真实交付入口
- 用手搓产物 / Mock 顶替
- 流程里先 restore / reset，让门禁在被治好的树上跑
- 只跑不核：命令跑了，输出没人看
- 满足字面而丢意图

⚠️ **还有一类不是执行端作弊，是清单自己有洞**：验收清单用「…」等省略写法。清单必须**可穷举**，或改为从配置/规格**自动生成**。实证：某次防魔数清单因省略号写得不全，一个硬编码默认值逃过检查，而**实现、测试、独立审查三方一起对着残缺规格「全部正确」**——没有任何一方在审查清单本身。

推论：**手工维护的中心清单会漂 ⇒ 生成或删除**，不要立「靠人记得更新」的清单。

判据是这条：**作弊比做对更难。** 做不到就换验收方式，不要靠叮嘱。

### 3. 数字必须带命令

要求完成区贴出**真实命令与输出**，每个数字附产生它的命令。禁止把预期值、文档记载值、口述值当实测值。

工具链未就绪或无法实跑时，要求措辞用「文档记载」，并**明令禁止出现「实测 / PASS / 跑通」字样**。

### 4. meta 预算

防造假与自审纪律**常驻在 `DS-common.md` 与项目 `DS.md`**，任务正文里只留一行引用。任务 md 要**技术信号压倒 meta**。

### 5. 声明执行环境与写入策略

必填 `**执行环境**`（决定本地/远端路由）。若该仓有写入限制（上游 clone 禁止 commit、产出必须落在仓外），在任务里点名，不要指望执行端自己去翻 `DS.md`。

### 6. 只写架构决策与测试场景

写：接口边界、不变量、被否的替代方案及其代价、测试场景（含边界与失败路径）。
不写：实现伪码、行号、逐步操作。

## 停止条件

- 某条写不出负测试 → 它不是验收条件，是期望。改写或删掉
- 需要伪码才能说清 → 停下来想架构，别开始写任务
- 作弊路径堵不住 → 换验收方式或换 worker，不要下发

## 与 `task-acceptance-replay` 互为负测试

验收时发现的每一个漏洞，回头必须能指出**任务设计里哪一条没写死**。指不出来，说明本 skill 缺了一条判据——补进「作弊搜索」的已知路径表。
