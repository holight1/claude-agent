# 语义化代码审查

**状态**：enabled
**消费者**：独立 reviewer（读各仓 `CODEX.md`）+ 架构师终审
**来源**：dsh `dsh-code-review`；正文于 2026-08-21 补写，触发事件见 §附录
**核心判断**：这个改动在**真实入口**上跑起来会怎样，而不是在测试里怎样？

---

## 1. 先锁定审查对象

- 锁定精确 base / head。retarget 或 merge 之后**重新确立并重跑**，不沿用旧结论
- **读接口两端**，不只读 diff。只看 diff 会漏掉"调用方还按旧契约用"这类缺陷
- 先跑一遍验收命令，**自己看输出**，不采信完成区转述的数字

---

## 2. 测试强度：三类失败，缺一类就漏

大多数检查清单只写了前两类。**第三类是最常漏的**。

| # | 失败形态 | 怎么查 |
|---|---|---|
| 1 | **断言被降级** | 断言改成打印、阈值放宽、断言删除、期望值改成实际值、`skip` / 预期失败标记 |
| 2 | **验收对象被偷换** | 用手搓产物替代真实被测系统；缩小到不触发问题的更简单情形；命令"绿"了但没走到目标路径；用替身对象顶替真实组件 |
| 3 | 🔴 **测试通过但不约束它声称的性质** | 断言在、没降级、对象没换，**但断言与注释/用例名声称的性质无关** |

### 2.1 反例证伪法（查第三类的唯一可靠办法）

> **把实现换成一个明显错误的版本，该测试会不会失败？**
> **不会 ⇒ 这条测试没有在守护它声称的性质。**

不需要真改源码，写几行临时脚本用坏实现跑一遍测试的断言逻辑即可。

优先对这几类用例做反例证伪：

- 名字里有 **stable / unique / independent / deterministic / isolated / distinct** 的
- 声称"**新增 X 不影响 Y**"的（坏实现：让 X 和 Y 共用同一状态）
- 声称"**A 与 B 不同**"的（坏实现：让 A 与 B 返回同一个东西）
- 只断言了"两次调用一致"，却声称测了"不同输入产生不同结果"的

**典型病灶**：一条断言同时被注释宣称测了两个性质，实际只测了其中一个——而没测的那个才是关键。

### 2.2 反向也要查

**缺失的测试和写坏的测试一样重要。** 对每条验收点问：这条如果实现写错了，现有哪条用例会红？答不上来就是缺口。

---

## 3. 数值常量：参数、门限、系数一视同仁

任何**无出处的数值**都要问出处，不区分它是不是"参数"。

- 参数（带宽、容量、时钟…）→ 必须来自配置 / 规格文件，不得硬编码进逻辑
- **门限与系数**（`> x * 1.5` 这类）→ 同样要出处。"看起来合理"不是出处
- 物理耦合比、单位换算常数 → 可以内嵌，但**必须带出处注释**，且披露在完成区

⚠️ **常见盲区**：防魔数的检查本身带一份常量清单时，**先审那份清单全不全**。清单不全 ⇒ 实现、测试、审查三方会一起对着残缺规格"全部正确"。

---

## 4. 合同缺陷：审查的固有盲区

**以任务书为唯一判据的审查，原理上抓不到任务书本身的缺陷。**

⇒ 每次审查**至少留一部分不依赖任务书**：直接回到设计基线、规格文件与代码本身核对。

具体做法：挑 2–3 个关键数值/算法，**自己独立算一遍**，与实现输出对照。不是"对着验收表打勾"。

---

## 5. 其余必查项

- **生命周期与所有权**：谁创建、谁释放、跨边界后归谁；重复计时 / 重复计入
- **真实入口与绕过路径**：这条逻辑在生产路径上会被走到吗？有没有旁路能绕开它
- **安全与可见面**：新暴露了什么；输入来源是否可信
- **文档同步**：改了行为有没有同步文档；文档说的和代码做的是不是一回事
- **回归**：有没有破坏之前已工作的路径

---

## 6. 输出纪律

- **按严重度排列**；**建议与阻断分开**
- **一条有实据的阻断胜过一串挑刺**
- 严格区分「**我核对到不对**」与「**我认为不对**」——前者给证据（命令 + 输出），后者标明是判断
- 结论只能是**通过**或**阻断**，不给中间态
