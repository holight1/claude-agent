# semantic-code-review · eval

## 正触发

| 场景 | 期望 |
|---|---|
| 审查代码 diff 或实现任务 | 触发；先锁 base/head，读接口两端 |
| 架构师终审带代码改动的任务 | 触发；并留一部分不依赖任务书 |

## 负触发

| 场景 | 为什么不该触发 |
|---|---|
| 只改文档措辞 | 属 `persistent-prose-review` |
| 核对调研结论的引文 | 属 `research-evidence-audit` |
| 决定任务当初该怎么写 | 属 `task-contract-design` |

## 诱人错误

| 场景 | 省力但错误的判断 | 本 skill 应给出的判断 | 判据 |
|---|---|---|---|
| 测试名为 `test_rng_stream_stable`，三条断言都在、没降级、对象没换 | 通过 | 断言与用例名声称的性质无关；把 `stream()` 换成忽略 `name` 的实现，三条照样过 | 判据：§2.1 反例证伪法 |
| 防魔数扫描集已从手工清单改为自动生成 | 更可靠了，可放行 | 集合从「手工列举」改成「自动生成」时**边界变得不可见**；必须显式列出集合内容并抽查 | 判据：§3.1 防造假机制 |
| 自检写 `assert 202.75 not in magic`，注释「derive 结果不应出现在数据文件里」 | 逻辑自洽 | 前半句对、**推论反了**：正因为它不在数据文件里，才更需要被单独纳入守护 | 判据：§3.1 防造假机制 |
| 验收表逐条打勾全过 | 可以判通过 | 判据来源是任务书，而任务书是被审查方的架构师写的；必须独立算 2–3 个关键值 | 判据：§4. 合同缺陷 |
| 清单里每一条都查过了 | 覆盖完整 | 清单盖不住**它自己不知道的那一类**；清单外的问题照样报并注明「不在清单内」 | 判据：§4.1 本清单同样有盲区 |
