# 文档体系架构

**状态**：dormant
**消费者**：架构师
**投影**：无
**来源**：dsh `dsh-doc-standards`；本框架 2026-08-21 的两处实测漂移
**核心判断**：这条事实的**归属地**是哪一篇？

## 何时用

**触发**：新增一类文档；文档要移动或拆分；发现同一事实出现在两处；索引与实际不符。

**不触发**：往已有文档里补一段内容。

## 要防的诱人错误

| 诱人错误 | 实证 |
|---|---|
| **手工维护中心索引** | `~/agent/agent-assets/practice-agent/code-agent/knowledge/README.md` 的主题表漏登记 `02-endpoint-facts.md`——**6 个文件、1 个人，索引就已经漂了** |
| 同一份判据存两份手工同步的副本 | `semantic-code-review` 的正文被抄进 `~/sim/CODEX.md`，两份从此各自演化 |
| 用变更日志代替就地改写 | 每个 `knowledge/10-changelog.md` 都在追加「某任务完成：新增了什么」，同一件事同时存在于 changelog、任务完成区、commit message 三处，且没有一处是权威 |
| 通用纪律落在项目文件里 | 三条普适的审查纪律只写进某个项目的 `REVIEWER.md`，框架模板一个字没变 |

## 判断程序

### 1. 事实归属：一条事实只有一个可编辑源

对每条事实问：**如果它变了，应该改哪一个文件？** 答案必须唯一。

出现两个答案 → 其中一个改成引用另一个，不要两边都写。引用时给**位置**（文件 + 章节），不要复述内容——复述会漂。

### 2. 索引：生成，或者删掉

手工维护的中心索引在**任何规模下**都会漂。

- 能从目录内容机械生成 → 写生成脚本，把索引标为生成物、禁止手改
- 不能生成 → **删掉索引**，靠文件名自述和目录结构导航

dsh 反对中心 INDEX 的理由是**合并热点**。本框架只有一个用户，那个理由不成立，但索引照样漂了——⇒ 真正的原因不是合并冲突，是**手工同步本身**。

### 3. 现行陈述 vs 讨论轨迹

**正文只回答「现在算什么」。** 用现在时描述当前认定的现实，过时的事实**就地改写**，不追加修订史。

「我们曾经怎么想」放在别处：`git log`、review 文件、归档、决策记录的 `## 备选方案`。

判据：正文每多一句「原先我们以为」，读者就要多分辨一次哪句是现在有效的。

### 4. 变更日志：默认不要

追加式变更日志几乎总是第三份副本（另两份是版本控制历史和产出本身的完成区）。三份会各自漂，且没有一处是权威。

例外：**对外发布**的 CHANGELOG（面向不读仓库历史的人）。内部知识库不属于此列。

### 5. 状态与权威等级

文档要能被一眼看出它算不算数。用闭集，写在固定位置：

| 状态 | 权威 |
|---|---|
| 讨论中 | ❌ 不可作依据 |
| 现行 | ✅ |
| **已落地** | ❌ —— **必须写明「权威已移交至 X」** |
| 已归档 | ❌ 冻结 |

`已落地` 是最容易缺的一档：一份建议稿变成了制度之后，它既不是「现行」也不是「尚未实施」，而下一个读它的人会拿一份半失效的东西当依据——**因为它读起来完全自洽，没有任何提示**。

### 6. 归档

归档冻结，且**免除演进中的门禁**。归档目录应从检索范围排除（`.rgignore` 之类），否则冻结的旧结论会被当成当前权威搜出来。

审查记录必须与被审查的那一版**配套冻结**——review 里每条意见都按那一版的章节号定位，拆开就对不上账。

### 7. 长度只是发现信号

超长文档提示可能承载了多个职责，但**长度本身不构成缺陷**。先找职责边界，再决定拆不拆。

## 停止条件

- 说不清一条事实该归谁 → 先定归属再动手，不要两边都写
- 拆分会让读者需要同时打开三个文件才能理解一件事 → 别拆
