# skills/ — 判断型 Skill 的规范源

本目录是**唯一的规范源**。三个客户端（Claude Code / Codex / opencode）都从这里取，不各存一份。

## 目录约定

```
skills/<name>/SKILL.md     规范源 —— 文件在这里 = 已吸收
enabled/<name> -> ../skills/<name>
                           启用池 —— 链接在这里 = 已启用
scripts/sync-skills.sh     把 enabled/ 投影到三个客户端 + 跑一致性检查
```

**为什么源与启用要分成两层**：frontmatter 拦不住加载——只要 skill 在客户端的加载路径上，它的 `description` 每轮都进上下文。两层目录让休眠 skill 的上下文成本**真的是零**，也让"删除 / 启用 / 继续休眠"这轮评审变成机械可核对的 `diff <(ls skills/) <(ls enabled/)`。

## 消费者与投影（两个闭集字段）

每个非 `dropped` 的 `SKILL.md` 必须有：

```markdown
**消费者**：架构师 | 共享
**投影**：无 | DS-common.md | REVIEWER-template.md（可逗号分隔多个）
```

| 消费者 | 含义 | 载体 |
|---|---|---|
| `架构师` | 只有 Claude Code 侧的架构师需要做这个判断 | skill 机制够用，`投影：无` |
| `共享` | 执行端或独立 reviewer 也要做这个判断 | **skill 机制到不了它们**，必须投影 |

**为什么共享的必须投影**：opencode 日志实测 `permission=skill` **为 0**（对照 `permission=bash` 一万两千次），而项目级 skill 目录**被加载过**、仍然 0 次调用。skill 内容唯一一次真正到达执行端，形态是任务明确要求它 `grep` 那个文件。⇒ **对执行端和 reviewer，唯一有效的载体是它们每轮必读的文件。**

`共享` 的 skill 必须有 `## 跨角色必读` 一节，**上限 45 行**——它会进执行端每轮必读的文件，只放真正跨角色的那部分，不是整个 skill。

## 生成块：单源，不手抄

`## 跨角色必读` 由 `scripts/render-shared.py` 渲染进投影目标的标记块：

```markdown
<!-- BEGIN SKILL-BLOCK: <name> -->
（自动生成，勿手改）
<!-- END SKILL-BLOCK: <name> -->
```

**目标文件里的这些块不要手改**——改 `SKILL.md`，然后跑 `scripts/render-shared.py`。门禁会校验块是否最新（重新渲染后内容不一致即红）。

这条不是洁癖。手抄产生第二个可编辑源：本仓曾让同一段判据散在 **3–5 处**并且已经开始不一致（`DS-common` 版本多了一句「贴出坏实现变红的实际输出」，另外三处没有）。而**项目文件是模板的拷贝**，标记块的边界同时让项目侧的重新同步变成「替换标记之间的内容」，不必逐节人工比对。

## 状态闭集

每个 `SKILL.md` 正文第一行必须是 `**状态**：<x>`，取值只有四个：

| 状态 | 含义 | 能否出现在 `enabled/` |
|---|---|---|
| `enabled` | 正文已写，已启用 | ✅ 必须 |
| `dormant` | 正文已写，未启用 | ❌ |
| `stub` | 只有占位，正文未写 | ❌ |
| `dropped` | 已判定不吸收，正文记录理由 | ❌ |

`dropped` 的条目**不删除**。理由要留在将来会被诱惑的地方——否则下一个人会独立地把同一个候选重新提一遍，而反驳它需要现场没有的信息。

## 载体边界：什么该做成 skill

判据一句话：**读完之后，执行者是否仍需做不能由固定规则穷举的判断？**

| 载体 | 负责什么 |
|---|---|
| 常驻规则（`DS-common.md` / `CLAUDE.md`） | 短而硬、所有任务都适用的底线 |
| **Skill（本目录）** | **提供判断程序、校准样例、适用与停止条件** |
| 脚本 / 门禁 | 闭集、格式、计数等确定性检查 |
| 项目适配层（`DS.md` / `REVIEWER.md`） | 仓库专属命令、路径、测试映射、写入策略 |

固定命令序列不做成 skill；需要语义判断的问题不硬编码成脚本。

## 硬规则：skill 正文不得出现具体项目命令

dsh 的 skill 跟被它约束的代码同仓同版本，改门禁就改 skill，一次 commit。**我们不是**——skill 在 `~/claude-agent`，被约束的对象在另外 N 个仓，两边会漂。

所以正文里不许出现 `pnpm` / `pytest` / `make test` / `cargo` 之类具体命令，只能写「见本项目 `DS.md §构建命令`」。`sync-skills.sh` 会检查，命中即红。

## 拓扑：为什么必须是用户级 / 绝对路径

架构师会话坐在**仓库之上**，而且不止一个根（`~`、`~/agent`、`~/sim`、`~/modules/base-sw`、Windows 审计路径）。仓库内的 `.claude/skills/` 不在它的加载路径上；要走项目级就得在每个根各放一份。

更硬的约束：受管仓库里有**上游 clone**（如 `deepseek-harness`），往仓里塞任何文件都是违规的——它连 `code-agent/` 都是靠仓外符号链接接进去的。

## 补写一个 skill 的顺序

**先列诱人错误，再写判据——不是反过来。** 诱人错误 = 有正当推理路径、下一个人会独立重新犯、且反驳它需要现场没有的信息的错。

补写完成的判据：

- 正触发和负触发样例各至少一个
- 至少一个「看起来合理但错误」的 eval
- 报告格式能分开「我核对到不对」「我认为不合适」「我无法自我验证」
- 辅助脚本打印处理单元数，**0 单元不得返回成功**
- **删掉关键判据后，负测试必须变红**

## Eval 约定（`enabled` 强制）

**每个 `enabled` 的 skill 必须有 `evals/EVALS.md`**，门禁校验。`dormant` / `stub` / `dropped` 不要求。

三节固定，缺一不可：

```markdown
## 正触发
| 场景 | 期望 |

## 负触发
| 场景 | 为什么不该触发 |

## 诱人错误
| 场景 | 省力但错误的判断 | 本 skill 应给出的判断 | 判据：§<正文小节标题片段> |
```

**「判据：§…」引用的小节标题必须在 `SKILL.md` 里真实存在**，门禁核对。这一条不是形式要求：它把 eval 和判据绑在一起——**判据被删掉或改名时，eval 会当场变红**，而不是留下一条指向空处的期望。

**「诱人错误」至少一条，且必须是真实发生过的**，不要编造。它的定义是：有正当推理路径、下一个人会独立重新犯、反驳它需要现场没有的信息。

首批 eval 直接用已经发生的事故，不要编造：表格格式导致引文校验实际匹配 0 条、`may` 被强化成「会」、英文与中文译文双计、`restore` 使门禁空转仍报绿、手搓入口替代真实交付路径。
