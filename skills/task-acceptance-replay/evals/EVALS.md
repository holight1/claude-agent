# task-acceptance-replay · eval

## 正触发

| 场景 | 期望 |
|---|---|
| 执行端返回任务、准备标通过 | 触发；先定位仓与写入策略，再复跑 |
| 准备 commit 执行端的产出 | 触发；先核箱内清单与完成区是否一致 |
| 准备把某条结论写进持久文档 | 触发；该结论的证据要能复跑 |

## 负触发

| 场景 | 为什么不该触发 |
|---|---|
| 自己刚写的单行改动 | 没有第二方产出，没有 ground truth 需要独立确立 |
| 本轮已亲自跑过且工作树未变 | 重复确认不产生新信息 |
| 核对一条引文是否逐字命中 | 那是 `research-evidence-audit` 的作用面 |

## 诱人错误

| 场景 | 省力但错误的判断 | 本 skill 应给出的判断 | 判据 |
|---|---|---|---|
| 校验脚本报 `40/40 逐字命中` | 通过 | 先问它**处理了几个单元**——该脚本的正则只匹配列表格式，被校验文件是表格，实际提取 **0 条** | 判据：§3. 复跑，核四样 |
| `verify 12/12 OK` | 工作树健康 | 该流程每个用例前先还原 `.pristine`，被污染的树被静默治好，这条绿色**没有信息量** | 判据：§4. 判定这条证据是不是真的 |
| 一条确定性测试三条断言全绿 | 该性质已被守护 | 把实现换成忽略入参的坏版本，它照样全绿 ⇒ 没在守护它声称的性质 | 判据：§5. 反例证伪 |
| 上游 clone 仓 `git status` 为空 | 干净、没问题 | 该仓产出挂在仓外符号链接上，`git status` **本来就看不见它**；别把「干净」当成「没产出」 | 判据：§0. 定位 |
| 执行端自审逐条打勾、reviewer 也判通过 | 三方一致，可以放行 | 三方判据同源于任务书；任务书自己有洞时三方会一起「正确」。必须独立算 2–3 个关键值 | 判据：§6. 留一部分不依赖任务书 |
| `assert max_credit <= 8192` 通过，测试名叫 `..._clamp` | 钳位已被验证 | 问它**离界多远**：峰值 `2.6e-10`，比值 `3.17e-14`；把 `saturation` 换成 `inf` 断言依然通过 ⇒ 钳位从未触发 | 判据：§3. 复跑，核四样 |
| 完成区贴了负测试实跑输出 `credit 1.467e9 B ≫ 8192` | 实跑过了，负侧成立 | 用交付签名（`dt_ps`）复算：实测是 `1.467e-3`，差 1e12 ⇒ **那次负测试跑在另一套单位口径上**，不是交付物 | 判据：§3. 复跑，核四样 |
| 整改记录写「已撤下 `hierarchy.py`」，`git show --stat` 无异常 | 整改已完成 | 整改改的是任务文件本身、不产生代码 diff。`grep -n` 实测原清单行仍在 ⇒ 声称的删除没发生 | 判据：§1. 先看减法，再看加法 |
| 打回指令写「补下界：峰值须 ≥ 0.5×8192」，执行端照做后通过 | 打回有效，整改到位 | 该指令的最弱实现是把 `0.5×8192` 写死 ⇒ 阈值与被约束量不同源；打回指令也是合同，写完要过充分性检查 | 判据：§打回指令也是合同 |
