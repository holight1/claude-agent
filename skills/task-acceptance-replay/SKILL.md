# 任务验收复跑

**状态**：enabled
**消费者**：共享
**投影**：DS-common.md
**来源**：dsh `dsh-pre-push-checks` + 本框架八起真实验收事故 + sim process-note 0010 / 0011
**核心判断**：这条绿色结果，证明的是不是我声称的那件事？

## 跨角色必读

### 验收对象不可偷换

**验收命令必须真实 exercise 任务要测的那个对象**，不得为"过门槛"而偷换或缩小被测对象：

| 严禁 | 例 |
|---|---|
| 用手搓/旁路产物替代真实被测系统 | 手写一个能过命令的结果，绕过本该被测的工具/流程 |
| 缩小到不触发问题的更简单情形 | 任务要测 A+B 交互，只测 A 让命令通过 |
| 让命令"绿"但没测到目标 | 退出码/输出对了，但来源不是任务要验证的路径 |
| **同一份代码，但调用方与实现的单位/时基口径不一致** | 实现签名是 `dt_ps`，测试传 `1e-8 # 秒` ⇒ 差 1e12。**这是无意的偷换**，写测试的人自己不知道 |

**量纲以被调用者的签名/规格为准，不得以调用点的注释为准。** 实证：独立 reviewer 专门核了量纲，写「`B/s × s` = 字节，口径一致」——它的「s」取自测试里那句 `# 秒`，而实现签名是 `dt_ps`。查了，而且查出一个自洽的错误。

**负测试的数字必须能用交付实现的签名复算出来。复算差整数个数量级 ⇒ 它跑的不是交付物。**

### 一条绿色结果成立的四个条件

1. **退出码取自被验证的那条命令**——避免管道，或用 `${PIPESTATUS[0]}`；`cmd | tail; echo $?` 取到的是 `tail` 的
2. **处理单元数不为 0**——校验工具要打印它处理了多少单元；**0 个 = 该验证无效**，不是通过
3. **作用于真实交付入口**——流程里若有 restore / reset / fixture 重建，被测对象可能在跑之前已被治好
4. **被约束量的量级落在断言的作用域里**——问：*这个数离断言的界有多远？* 差整数个数量级 ⇒ **该断言无信息量**，通过不构成证据

对每条绿色结果问一次：**如果实现是错的，这条命令会不会红？** 答不上来 ⇒ 它不构成证据。

### 声称「撤下 / 删除 / 改名」时，证据必须是「查不到」

不是「我改了」。要贴 `grep -c` 为 0，或 diff 里的删除行。

实证：整改记录写「完成区文件清单**撤下** `hierarchy.py`」，实测该行原封不动还在（`grep -n` 命中两处：原清单行 + 声称撤下的那行）。**在只需要动一行文字的动作上，决定与执行之间的距离短到人会以为自己已经做了。**

## 何时用

**触发**：执行端返回任务；准备把任务标成通过；准备 commit 执行端的产出；准备把某条结论写进持久文档。

**不触发**：自己刚写的单行改动；本轮已亲自跑过且工作树未变的重复确认。

## 范围合并

本 skill 吸收了 `relevant-check-selection`（dsh 的 `dsh-pre-push-checks`）。dsh 的落地终点是远端 PR + CI，选检查项是执行端 push 前的事；本框架的执行端不 push，**架构师才是门禁**，选检查和跑检查是同一个人同一时刻的两半。

## 要防的诱人错误

这些不是疏忽。每一条都有正当的推理路径，下一个人会独立地重新犯，而反驳它需要现场没有的信息。

| 诱人错误 | 它为什么看起来对 | 现场缺什么 |
|---|---|---|
| **「X 通过」=「X 正确」** | 命令退出 0 了 | 这条命令在实现是错的时候会不会红 |
| 校验作用于**错误的对象** | 脚本跑完了，报了个漂亮的数 | 它到底处理了几个单元；曾出现正则只匹配列表格式、被校验的文件是表格 → 实际处理 0 条却报「40/40 命中」 |
| 门禁**空转**仍报绿 | 逐条都是 OK | 流程里有没有 restore / reset：曾有校验在每个用例前先还原 `.pristine`，被污染的工作树被静默治好，`12/12 OK` 因此毫无信息量 |
| 数字没有**产生它的命令** | 数字来自完成区或口述，看着具体 | 曾把口述的「3 人几个月」当事实，实测 `git log --format=%an \| sort -u` 是 43；曾把 1446 篇当英文篇数，实际 723，另一半是译文 |
| **跨仓错位** | 规则读起来很合理 | 它是哪个仓的事实；曾把 dsh 的目录语义写进另一个仓的规则，且还搞反了 |
| 退出码取自**管道末端** | `cmd \| tail; echo $?` 写法很自然 | `$?` 是 `tail` 的，不是 `cmd` 的 |
| 完成区自审当证据 | 执行端逐条打了勾 | 那是线索，不是 ground truth |
| **上下界断言通过 = 该性质被守护** | 断言写着 `<= 8192`，测试名字也点了钳位 | 被约束量离界几个数量级；曾出现峰值 `2.6e-10` 对界 `8192`，钳位开关实测同一个数 |
| **负测试贴了实跑输出 = 负侧成立** | 数字很具体，不是「我认为会红」 | 那个数能否用**交付实现的签名**复算出来；曾出现完成区与 reviewer 同贴 `1.467e9`，交付实现实测 `1.467e-3`，差 1e12 |
| **整改记录里的动作 = 已发生** | 「已撤下 / 已改名」写得斩钉截铁 | 整改常不产生代码 diff（改的是任务文件本身），`git show --stat` 看不出；要 `grep -n` 查它是否真的**查不到** |

## 判断程序

### 0. 定位：我在哪个仓，这个仓应该长什么样

本框架的架构师**坐在仓库之上**，一个会话里同时碰多个仓——这一面 dsh 的 skill 没有。

- 所有 git 命令**显式带仓路径**（`git -C <repo> …`），不依赖 cwd
- 先取该仓的写入策略（见项目 `DS.md`），它决定「健康长什么样」：

| 仓类型 | 复跑前应看到 |
|---|---|
| 自有仓，执行端可 commit | 恰好一个属于本任务的新 commit，箱外无残留 |
| 上游 clone，禁止 commit | `git status --short` **为空**；非空即事故 |
| 产出挂在仓外（符号链接） | `git status` **看不见它** —— 它的证据必须另外取，别把「干净」当成「没产出」 |

### 1. 先看减法，再看加法

`D` 状态是回归的高频根因：执行端为解锁当前任务删掉了之前能工作的东西。

- 找删除项
- `git show --stat <sha>` 对照完成区的修改文件清单
- **箱外残留 = 完成区不完整** → 打回，不要替它补 commit

**⚠️ 整改记录声称的删除动作要单独复核，`git show --stat` 看不出来。** review 后的整改往往改的是**任务文件自己**（撤下一行清单、改一句措辞），不产生代码 diff。对整改记录里每一条「撤下 / 删除 / 改名」，自己跑一次 `grep -n` 看它是否真的查不到。

实证：整改记录第 1 条写「撤下 `hierarchy.py`」，`grep -n` 实测原清单行仍在；同一条记录的第 2 项（改必填）却是真做了的，diff 可证。**所以不是整体敷衍，是单条落空**——因此必须逐条查，不能因为抽到一条真的就放过整段。

### 2. 选检查项

从 outgoing diff 推：改了哪一层 → 该层**最窄而充分**的检查。

- 不盲跑全套（掩盖归因，也掩盖「这一项其实没覆盖到」）
- 不重复本轮已经取得的证据
- **每一项必须能一句话回答「它证明了什么」**；写不出来就别跑，跑了也不构成证据

### 3. 复跑，核四样

命令、**退出码**、**处理单元数**、**被约束量的量级**。

- 退出码要取自被验证的那条命令：避免管道，或用 `${PIPESTATUS[0]}`
- **处理单元数为 0 = 该验证无效**，不是通过。要求校验工具打印它处理了多少单元
- 输出里的每个数字，要能对上它声称处理的对象
- **第四样只对「x ≤ B」「x ≥ B」这类断言问**：*这个数离界有多远？*
  - 差整数个数量级 ⇒ **该断言无信息量**，它的「通过」不是证据
  - 实证：`credit 峰值 2.6e-10` 对界 `8192`，比值 `3.17e-14`；把 `saturation` 换成 `inf` 断言依然通过 ⇒ 名字叫 `..._clamp` 的测试里，钳位从未被触发过
  - 上界断言天然单向：**「永远不接近界」和「被正确钳住」在它看来一模一样**

**同时核一次口径**：负测试贴的数字，用交付实现的签名手工复算一遍。复算差整数个数量级 ⇒ 它跑的不是交付物（见「验收对象不可偷换」末两段）。

### 4. 判定这条证据是不是真的

对每条绿色结果问一次：

> **如果实现是错的，这条命令会不会红？**

答不上来 → 它不构成证据。常见的答不上来的形态：

- 流程里有 restore / reset / fixture 重建，被测对象在跑之前被治好了
- 跑的是手搓产物、Mock、缩小到不触发问题的样例
- 走的是旁路入口，不是真实交付入口
- 只跑不核：命令跑了，但没人看输出内容

### 5. 反例证伪

每条被声称关闭的验收项，**至少破坏一次让它变红**。做不到的那条，说明它当初就不是验收条件。

判据写成一句可执行的话：

> **把实现换成一个明显错误的版本，这条测试会不会失败？**
> **不会 ⇒ 它没有在守护它声称的性质。**

⚠️ **这一问预设「实现有错」，所以它抓不到实现正确、测试构造不到位的那一类。** 上下界断言就是这一类：实现忠于规格，测试从未把被测量推进断言的作用域，于是坏实现（`saturation=inf`）与好实现给出同一个数、断言双双通过。⇒ 反例证伪之外还要问核四样的第四问（离界多远），两问都要问。

不必真改源码，写几行临时脚本用坏实现跑一遍断言逻辑即可。

**优先证伪对象的清单不在这里**——它由 `semantic-code-review §2.1` 单独维护，本 skill 不再抄一份。清单比原则管用，但**两份清单比没有清单更糟**。

**反向也查**：对每条验收点问「实现若写错，现有哪条用例会红」——答不上来就是缺口。

### 6. 留一部分不依赖任务书

**以任务书为唯一判据的验收，原理上抓不到任务书本身的缺陷。**

判据来源是任务书，而任务书是架构师自己写的——这条链上没有任何一环以任务书为审查对象。它不是谁失职，是流水线的固有盲区。

⇒ 每次终审**至少留一部分不对着验收表打勾**：挑 2–3 个关键数值或算法，**自己独立算一遍**，与实现输出对照；关键常量回查出处；回到设计基线与规格文件核对。

实证：某次终审的三条发现全部来自这一步——手算块量化、反例证伪 RNG 测试、回查一个门限常数的出处。同一批产出被执行端自审和独立 reviewer 都判过「通过」，因为**三方对着同一份残缺规格，各自都是正确的**。

## 停止条件

- 任一步拿不到证据 → **停**，在报告里写进「我无法自我验证」，不要用推断补
- 出现删除项或箱外残留 → 直接打回
- 需要修改被验收的对象才能跑通 → 停；这已经不是验收

## 报告格式

三类分开写，不混在一起：

- **我核对到不对**（有命令与输出）
- **我认为不合适**（判断，无实据）
- **我无法自我验证**（必填；空着会让「通过」被读成全面核对过）

## 不属于本 skill

- 代码语义缺陷 → `semantic-code-review`
- 引文、计数与事实核对 → `research-evidence-audit`
- 任务当初该怎么写 → `task-contract-design`

## 终审必做的最后一步

**本轮的每个发现，能指回任务设计的哪一条？**

- 指得出 → 记下来，那条判据下次要写死
- **指不出来 → 判据表本身缺项**，按 `process-gap-capture` 落一条 process-note，别只在口头指出

这一步不是可选的收尾。流程缺口写在任务终审区就会散落在几百行任务文件里，采纳时要翻任务，而且**机制依赖有人记得提醒**。
