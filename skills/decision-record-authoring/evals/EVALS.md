# decision-record-authoring · eval

## 正触发

| 场景 | 期望 |
|---|---|
| 改动改变了跨文件 / 跨角色的约定 | 触发；写记录 |
| 改动改变了门禁或测试策略 | 触发 |
| 你推翻了一条已有的决定 | 触发；同轮做取代检查 |

## 负触发

| 场景 | 为什么不该触发 |
|---|---|
| 重命名、格式化、纯补测试 | 机械改动 |
| 只影响单个函数内部、外部无感知 | 无人会重议 |
| 记录一次踩坑现场 | 属 `process-gap-capture`，它写的是流程缺口不是决定 |

## 诱人错误

| 场景 | 省力但错误的判断 | 本 skill 应给出的判断 | 判据 |
|---|---|---|---|
| `## 备选方案` 想不出内容 | 编两条看起来合理的填上 | 编造的备选**比空着更坏**——它让后来者以为某条路已被论证过。写「无备选：<理由>」 | 判据：§4. 备选方案 |
| 记录里的路径已过时 | 追加一段「原先是 X，现已改为 Y」 | 事实**就地改对**，不追加变更史；只有**决定**不可改写 | 判据：§2. 事实与决策分开对待 |
| 新决定推翻了某条旧记录 | 先写新的，回头再整理旧的 | 取代检查在**写入时**做；事后审计永远排在别的事后面 | 判据：§1. 先做取代检查 |
| 记录写清了「改了哪些文件」 | 内容完整 | 改了什么 `git log` 里有；记录要回答的是**当时还有哪些选择、为什么没选** | 判据：§3. 写「为什么」 |
| 有人想重提一条已被否的方案 | 引用记录直接驳回 | 记录是**讨论依据不是自动否决**；再提案允许，但必须正面击败当时放弃的那个代价 | 判据：§6. 决策记录不是自动否决 |
