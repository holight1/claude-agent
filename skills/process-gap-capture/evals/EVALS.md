# process-gap-capture · eval

## 正触发

| 场景 | 期望 |
|---|---|
| 验收点被精确满足字面但意图落空 | 触发；合同缺陷 |
| 独立审查漏掉一整类问题 | 触发；检查清单缺项 |
| 修复一个缺陷后同类缺陷换位置又出现 | 触发；**最高优先级** |

## 负触发

| 场景 | 为什么不该触发 |
|---|---|
| 单纯的实现 bug、笔误 | 写在任务终审区就够了 |
| 一次性判断失误 | 同一个人下次不会再犯 |
| 决定框架该怎么改 | 那是 `decision-record-authoring`，且项目会话不直接改框架 |

## 诱人错误

| 场景 | 省力但错误的判断 | 本 skill 应给出的判断 | 判据 |
|---|---|---|---|
| 「本可以拦住它的是什么」答案是「当前无」 | 写不出来，那就别记了 | 「当前无」是合法且往往最有价值的答案——全新形态的缺口本就该没有对应控制。要写清**为什么**没有 | 判据：§停止条件 |
| 缺口分析写在任务终审区 | 已经记下来了 | 终审区写「这次的判决」，不写「下次怎么不再发生」；混写会让它埋进几百行任务文件、采纳时要翻任务 | 判据：§与终审的关系 |
| 在项目里发现框架缺陷，顺手改了 `~/claude-agent` | 一步到位 | 项目会话只产出**可采纳的建议**；框架改动权在用户 | 判据：§硬规矩 |
| 一次终审发现三个缺口 | 合成一条记录写完 | 一条记录一个缺口，合并会让采纳时无法逐条取舍 | 判据：§硬规矩 |
| 建议写成「以后要更仔细」 | 也算记下来了 | 不是可采纳的改动，重写或丢弃 | 判据：§停止条件 |
