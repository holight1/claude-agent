# `enabled` 的 skill 必须带 eval，且 eval 引用的判据必须真实存在

**状态**：现行
**日期**：2026-08-21
**触发**：外部 review 提出「每个 enabled skill 要有正触发、负触发和至少一个『看起来合理但错误』的 eval」作为验收标准，而当时 6 个 enabled skill **一个 eval 都没有**（`find skills -name evals` 为空）。同一份 review 又建议再启用两个——那会把未验证面从 6 扩到 8。
**证据**：外部 review §二 R2 与 §五验收标准；`skills/README.md` 早已写着这条要求但无门禁。
**作用面**：`skills/README.md` §Eval 约定；`scripts/sync-skills.sh`；八个 enabled skill 各自的 `evals/EVALS.md`。

## 决定

**先建 eval 约定并补给现有 enabled，再启用新的。** 顺序不是「启用后补 eval」。

`enabled` 状态强制要求 `evals/EVALS.md`，三节固定：`## 正触发` / `## 负触发` / `## 诱人错误`。`dormant` / `stub` / `dropped` 不要求。

**「诱人错误」每条必须写 `判据：§<正文小节标题片段>`，门禁核对该小节在 `SKILL.md` 里真实存在。**

## 为什么

**顺序反转的理由**：eval 是判断「这个 skill 值不值得占每轮上下文」的唯一材料。先启用后补，等于先付成本再决定要不要买。而且未验证的 enabled 数量越多，越难归因——效果变化说不清是哪个 skill 带来的。

**为什么强制引用判据小节**：这条不是形式要求，它把 eval 和判据**绑在一起**。判据被删掉或改名时，eval 当场变红，而不是留下一条指向空处的期望。没有这个绑定，eval 会随 skill 正文演进而悄悄失效——那正是本框架反复遇到的「手工同步两份内容」的病。

**「诱人错误」必须真实发生过，不许编造**：编造的诱人错误既不能证明 skill 有用，也不能在判据被削弱时变红。八个 skill 的 eval 全部取自已发生的事故。

## 备选方案

- **eval 写成可执行脚本，让门禁真的跑一遍判断**。放弃：skill 的产物是判断而非输出，没有稳定的机械判定面。现阶段做结构 + 引用可达性检查，把「判据被删则 eval 变红」这一条做成机械的，其余靠人读。若将来出现可机械判定的 skill，再单独加。
- **只要求「诱人错误」一节，不要正/负触发**。放弃：误触发和漏触发是 skill 的主要成本，而它们只能由触发样例暴露。
- **不做门禁，写进 `skills/README.md` 当纪律**。放弃：那条要求**本来就已经写在 README 里**，而 6 个 enabled 一个 eval 都没有——纪律不带门禁等于没有。

## 验收证据

`scripts/sync-skills.sh` 新增三项检查，两条负测试逐条验过：

- 删掉 `SKILL.md` 里被引用的小节标题 → 报「「判据：§…」在 SKILL.md 里找不到对应小节标题」
- `EVALS.md` 缺一节 → 报「缺 '## 诱人错误' 小节」

八个 enabled skill 现均有 `evals/EVALS.md`，全部通过引用可达性检查。

**未验证**：eval 本身的质量。结构齐备不等于样例选得准——误触发与漏触发要在真实任务里才暴露。
