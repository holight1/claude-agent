# Worker 路由与独立审查只保留一套判据

**状态**：现行
**日期**：2026-08-21
**触发**：`USAGE.md` 保留着两条按代理量路由的旧规则——「改动超过 3 行 → 下发任务」与「纯文档任务可跳过 Codex」——与 `worker-routing-and-delegation` 的判据冲突，导致该 skill 无法启用（两套判据并存等于看心情）。
**证据**：外部 review 的 R1；`USAGE.md` 原第 127 / 166 / 168 行。
**作用面**：`USAGE.md` §3.0 与 §3.1；`skills/worker-routing-and-delegation/SKILL.md` 状态 dormant → enabled；架构师 memory。

## 决定

删除两条旧规则，框架内只保留一套判据：

- **路由**：这件事做完之后，**我能不能用命令独立核对它做没做到？** 能 → 可下发执行端；不能 → 改任务设计 / 换 subagent / 自己做
- **独立审查的触发**：这次交付里，**有没有架构师自己无法验证的部分？** 有 → 引入并点名那一部分；没有 → 不引入

架构师每轮明确说出「本轮我无法自我验证的是 X」，由用户判断是否需要额外交叉审查——**这个判断不由架构师独占**。

## 为什么

**行数不是可验证性的代理。** 三行改一个不变量，比三百行加测试危险得多。按行数路由会在真正危险的改动上放行，在安全的改动上制造仪式。

**文件类型不是无法自证性的代理。** 文档同样含无法自我验证的事实主张——本框架已发生过的引文缝合、情态加强、计数双计全在文档里。「纯文档跳过审查」恰好放过了本框架最高频的一类失效。

两条旧规则的共同毛病是**用容易测量的量代替真正要判断的量**。可测量性是它们唯一的优点，而那个优点在两个反例面前不成立。

## 备选方案

- **保留行数规则作为「快速通道」，复杂情况再用新判据**。放弃：两套判据并存时，人会选先想到的那个，而先想到的总是更省力的那个。且旧判据放行的恰是新判据要拦的。
- **把独立审查改成一律引入**。放弃：审查有成本，且无差别引入会让「本轮我验证不了什么」这个判断消失——而那个判断本身才是有价值的产物。
- **等 `worker-routing-and-delegation` 积累真实使用数据再删旧规则**。放弃：skill 因冲突而不能启用，不启用就没有数据，是死循环。

## 验收证据

`grep "3 行\|纯文档任务可跳过" USAGE.md` 改动后无命中。`worker-routing-and-delegation` 已 enabled，其「与 `USAGE.md` 的关系」一节由「待决冲突」改写为「框架内只有这一套判据」。

**未验证**：新判据在真实路由决策上的效果。它此前从未生效过——旧规则一直在。
