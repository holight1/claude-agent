# skill 承载判据，不承载案例 —— 与 dsh 的差异及原因

**状态**：现行
**日期**：2026-08-21
**触发**：用户指出「skill 是不是太具体了，我看有好多具体数据」，并追问「包括那个整理流程的 skill，也应该排除具体问题、只归纳流程级别的问题？」，随后要求**先看 dsh 怎么做**再定。
**证据**：`~/agent/deepseek-harness/.agents/skills/dsh-code-review/SKILL.md`（49 行）、`dsh-pre-push-checks/SKILL.md`（123 行）、`dsh-prose-standard/SKILL.md`（81 行）；`~/agent/deepseek-harness/.agents/notes/implemented/process/2026-06-11-quality-gates.md`（Agent Note 的 `## Problem` / `## Decision` / `## Consequences` 结构与顶部取代链接）。**本仓不复制其内容，以那些文件为准。**
**作用面**：`skills/*/SKILL.md` 全部 8 个 enabled skill（剥离案例数据 + 新增 `## 判据来源` + 野心上限声明）；`scripts/sync-skills.sh`（新增案例数据判别式与 `## 判据来源` 强制）；经生成块投影到 `collab-framework/DS-common.md`。

## 决定

**一 · SKILL.md 正文放三样：可执行判据、领域无关的失败形态、以及理解判据所必需的最小校准例。** 项目可识别的事故叙事、原始测量过程、成组实测数字进 `decisions/` 与 `evals/`。

| 层 | 内容 | 放哪 |
|---|---|---|
| **判据** | 「把被约束量改成永远不接近界的值，这条断言会不会红？」 | SKILL.md |
| **形态** | 「上界断言 + 量永远远离界 ⇒ 空转」「阈值与构造参数不同源 ⇒ 界一变红在错处」 | SKILL.md ——「点名具体手法」要的是**这一层** |
| **最小校准例** | `x ≤ B` 配 `x ≥ k·B`；`x ≥ B` 配 `x ≤ B/k`；提取器格式假设与被校验文件不符 ⇒ 处理单元数 0 | SKILL.md，可选 `## 校准例`，**≤2 条、每条 ≤3 行** |
| **事故叙事 / 原始测量** | 项目名、任务号、路径、日期、成组实测数字、测量过程 | `decisions/` 的「为什么」节 + `evals/EVALS.md` 的场景列 |

**共享投影块（`## 跨角色必读`）用更严标准**：只留判据 + 至多一个极短反例；零实测值形态、零受管项目路径。它对对应角色是**每任务必读**，预算近乎绝对。

⚠️ **校准例不是事故存档，是判据的一部分。** 判据说「配对侧约束」，不给 `x ≥ B` 配 `x ≤ B/k` 这一行，读者就分不清「对侧」指什么——外部 review 恰好用这条反驳了本记录的初版（初版写「零案例」，而实际实现一直保留着这些校准例，**文档比实践更严**，违反本框架自己的「结论正确 ≠ 文件等于该结论」）。

**二 · 每个 enabled skill 必须有 `## 判据来源`**，列出对应的 `decisions/` 记录，且引用必须在**本节内**（按小节边界提取，不是固定行数窗口）。规则要辩论时去那里辩，不在 skill 里堆证据。（照抄 dsh 的 `## Sources of truth`。）

**三 · 每个 skill 声明野心上限**：「本 skill 是判据，不是完整清单。」（照抄 dsh 的 "This skill is guidance, not a complete checklist."）

**四 · 门禁只查可机械证明的结构，不声称能判「正文有没有案例」。**

| 门禁 | 可证明吗 |
|---|---|
| `## 判据来源` 存在，且**本节内**有可解析的 `decisions/` 引用 | ✅ |
| `## 跨角色必读` 行数预算 | ✅ |
| `## 跨角色必读` 内零实测值形态、零受管项目路径（`~/claude-agent` 之外的 `~/X/`） | ✅ 该节预算近乎绝对，硬失败 |
| 可选 `## 校准例` 的条数（≤2）与非空行数（≤8） | ✅ |
| 生成块基数与一致性（`render-shared.py`） | ✅ |
| **正文其余部分「是不是案例」** | ❌ **由 review 判断，门禁不管** |

🔴 **删掉了初版那组数字硬失败。** 它冒充案例门禁而做不到：外部 review 当场给出三条绕过——大写 `1E12`、「某项目实测值为 8192，见某条 decision 记录」（我自己设计的负测试就是让这种通过的）、以及**不含任何数字的事故叙事**；同时它会误伤协议常量与版本号。三条我都复现了。

## 为什么

### 与 dsh 的差异：不是抽象程度不同，是载体层级不同

**dsh 的 skill 一点都不抽象。** 三个 skill 里满是具体：本仓命令（`pnpm --silent run change-scope --base <verified-base-ref>`）、本仓配置事实（`packages/*/*/src` per-file 100% 覆盖率、`vitest` 不做 typecheck）、外部系统行为事实（PR 处于 `CONFLICTING` 时 GitHub 不创建 workflow run，`total_count` 恒 0）、点名的偷懒手法（不得用 `--passWithNoTests` / 降阈值 / 缩 `--coverage.include` 去藏没覆盖的文件）。

**但事故叙事三个 skill 加起来 0 处。** 没有一句「我们曾经测到 X 是错的」。

决定性的差别是**载体层级**：

| | dsh | 本框架 |
|---|---|---|
| skill 位置 | `.agents/skills/`，**项目级**，仓内 | `~/claude-agent/skills/` → `enabled/` → 用户级客户端目录 |
| 可达范围 | **只在该仓** | **每个仓的每个会话都能触发它** |
| 「合法的具体」 | 该仓的命令、路径、门禁阈值、工具行为 | **框架自身**的脚本名、目录、闭集、角色、`--check/--handoff` 三档 |
| 某个受管项目的实测值 | 不存在这个问题 | **禁止**——与别的仓无关，还会被当成通用事实 |

⇒ 我把「项目级 skill 可以写项目事实」错抄成了「用户级 skill 可以写**某个**项目的实测值」。这条错误还命中了本框架自己列的诱人错误「**跨仓错位**」。

### 上下文成本按载体分层（初版这里写错了）

初版把「整个用户级 SKILL.md 每仓每轮加载」当作主要理由。**那是错的**，外部 review 指出后核实：

| 载体 | 何时进上下文 |
|---|---|
| `description` | **全局发现阶段**，每轮都在 |
| SKILL.md 正文 | **skill 被触发后**才读 |
| `DS-common.md` / `REVIEWER-template.md` 的投影块 | 对**对应角色每任务必读** |
| `decisions/` / `evals/` | 按需读取 |

⇒ 最严的预算属于 **`description`** 与**共享投影块**，不是 SKILL.md 全文。

**这条纠正没有推翻结论，但换掉了它的主要理由。** 剩下站得住的三条：

1. **跨仓相关性**——某个受管项目的实测值对别的仓是噪声，且会被读成通用事实（「跨仓错位」）
2. **单一可编辑源**——那些数字在 `evals/` 与 `decisions/` 里已有家，正文那份是第二个会漂的源
3. **共享投影块的成本是真的每任务**——它确实按角色每任务必读，所以该处的严格标准照旧

### 「为什么」在 dsh 放哪：Agent Notes = 我的 `decisions/`

`2026-06-11-quality-gates.md` 的结构是 `## Problem` / `## Decision` / `## Consequences`，顶部带取代链接（`The hook/CI symmetry in this record is superseded by …`）。事故证据在 `## Problem`：「Early evidence: tests that didn't typecheck shipped (vitest doesn't typecheck) and were only caught by a review.」而 `dsh-code-review` 只在 `## Sources of truth` 里链到这条 note，正文一个字都不重复它。

**本仓的结构本来就是对的**（`decisions/` + `已取代` 闭集 + 引用不复制），我只是没用它——把 `## Problem` 的内容抄进了 skill 正文。

### 这次搬家是无损的：SKILL.md 那份本来就是冗余副本

搬家前逐个核对每个实测值是否另有出处：

| 实测值 | `decisions/` | `evals/` |
|---|---|---|
| 界与峰值、比值、口径差 | ✅ | ✅ |
| 整改声称撤下但未撤 | ✅ | ✅ |
| 计数口径（目录篇数 vs 单语言篇数） | 部分 | ✅ |
| 口述人数 vs 实测贡献者数 | ✗ | ✅ |
| 门禁在还原过的树上空转 | ✗ | ✅ |
| 提取器格式假设不符、报满分 | ✗ | ✅ |

**每一条在 `evals/` 里都已有家。** 所以 SKILL.md 里那份是第二个可编辑源 —— 正是本仓已采纳的「止血副本会漂」那个病。三轮里犯第二次：上一次是同一段判据散在 3–5 处（靠生成块修掉），这次是实证。

`evals/` 是正确的去处还有一个独立理由：**eval 就该具体**——没有具体数据的 eval 恰好是外部 review 刚抓到的那种空数据行；而 `evals/` 只在按需读取时进上下文。

⚠️ **「无损」只成立在存储这一层，不成立在能力这一层。** 外部 review 指出：`evals/EVALS.md` 目前只是**静态表格，没有跑模型行为的 eval harness**，所以「案例已有新家」**不等于**「精简后判断能力没有下降」。初版把这两件事混成一句「搬家无损」，是本框架自己禁止的那种偷换（验证对象不是同一个）。⇒ 保留最小校准例正是对这个风险的对冲；能力是否下降仍**未验证**，见下方验收证据末段。

### 为什么不是「把规则写抽象些」

框架原有的信条是「**点名具体手法，不写抽象原则**」，它有实测依据：抽象版失败过——`task-contract-design` 早就有「盯住复发」，项目侧**确实盯住了**，然后仍然只能再补一格。所以答案不是回到抽象，而是**分清「形态」与「案例」**：形态可执行且与领域无关（dsh 那句 "Probe tiny and exact limits, oversized single chunks, and multibyte text for byte limits" 就是形态），案例只是它的一次出现。

规则弱的修法是**更锐的检查，不是附一段轶事**。

## 备选方案

- **零案例：连最小校准例也移走（本记录初版）。** **已被推翻**：外部 review 指出某些最小例承担的是**校准**作用而非事故存档（`x ≥ B` 该配什么、格式假设不符为什么导致处理单元数 0），移走会让 skill 退化成抽象原则；而「案例已有新家」在**没有 eval harness** 的前提下不等于判断能力没下降。更直接的反驳：**实现一直保留着这些校准例，初版文档比实践更严** —— 违反本框架自己的「结论正确 ≠ 文件等于该结论」。⇒ 改为「判据 + 形态 + 最小校准例」，并给校准例设上限（≤2 条、≤3 行）防它长成案例库。
- **保留全部案例，只把 `## 跨角色必读` 清干净。** 放弃：投影块的成本确实最高，但正文里的项目实测值仍然是**第二个可编辑源**且对别的仓是噪声——这两条与加载频率无关。不过这个备选比初版以为的更有道理：上下文成本这一条论据只对投影块和 `description` 成立（见上）。
- **用数字正则做案例门禁（本记录初版）。** **已删除**：外部 review 给出三条绕过（大写 `1E12`、带出处的实测值、不含数字的事故叙事），并指出会误伤协议常量与版本号——三条我都复现了。这是「案例检测」在本轮失效的**第三个位置**（前两个都在引用可达性门禁），按 `gate-design-and-negative-testing §3`「第三次换位置视为设计债」，**停止扩大正则**，改为「门禁只查可证明的结构，语义边界由 review 判断」。
- **用领域名词黑名单做门禁**（`credit`、`saturation`、`dt_ps`…）。放弃：手工维护的清单，下一个项目引入的名词一律漏过——本仓刚用两轮把同类问题从「手工清单」改成判别式，不能在这里反向走。
- **把案例移进 skill 目录下的 `CASES.md`，不进 `decisions/`。** 放弃：那会造出第三个地方，而 `decisions/` 已承载「为什么 + 备选 + 取代链」并被 `check-decisions.sh` 守护。多一个未被门禁覆盖的目录 = 多一个会漂的源。
- **给门禁留一个显式豁免标记**（如 `<!-- allow-case -->`）。**暂不做**：豁免标记会成为第一选择。现在改成「门禁不管语义」之后，这个备选也失去了必要性。
- **给 `evals/` 建真正的 eval harness**（跑模型、比对判断）。**暂不做**：本框架当前没有跑 eval 的执行面，且 `permission=skill` 实测为 0 说明 skill 的调用信号本身就取不到。这是「精简是否影响判断能力」唯一能真正回答的办法，记为未偿的技术债。

## 验收证据

`sync-skills.sh --check`：19 个规范源 / 8 个启用 / **0 处错误**；`check-framework.sh --handoff` 通过。

搬家结果（8 个 enabled skill 的 SKILL.md）：领域名词与实测数字从 **42 处 → 0 处**；`DS-common.md` 生成块里的 6 处泄漏随重新渲染消失。第二轮外部 review 又点出三处此前漏掉的事故叙事（`真实案例` 表头、`## 附录 · 补写触发事件`、带日期与项目名的 `## 实测修正`），已分别改为失效形态、`## 校准例`、判据理由，原始细节移进对应 `evals/`。

⚠️ **我第一轮的核对本身是「作用集合比声称范围窄」**：我用的 grep 键是一串领域名词（`credit|saturation|dt_ps|…`），它结构上看不见「真实案例」这种小节标题、也看不见日期与项目名。这就是本框架花了三轮在治的那个病，出现在**我核对这条规则本身的那一步**。

门禁负测试（隔离副本，均已还原）：

| 输入 | 期望 | 实测 |
|---|---|---|
| `跨角色必读` 内出现实测值形态的数字 | 红 | ✅ `[FAIL] §跨角色必读 出现实测值形态的数字` |
| `跨角色必读` 内出现 `~/<别的仓>/` 路径 | 红 | ✅ `[FAIL] … 出现受管项目路径（~/sim/）` |
| `跨角色必读` 内出现 `~/claude-agent/`（框架自身） | **放过** | ✅ FAIL 数 0 —— 不误伤 |
| `## 校准例` 2 条、每条 3 行 | **放过** | ✅ FAIL 数 0 |
| `## 校准例` 3 条 | 红 | ✅ `[FAIL] … 有 3 条，上限 2` |
| `## 校准例` 有一条 4 行 | 红 | ✅ `[FAIL] … 最长的一条有 4 行` |
| `## 校准例` 有节但无条目 | 红 | ✅ `[FAIL] 有 '## 校准例' 一节但没有 '- ' 条目` |
| `## 判据来源` 改名 | 红 | ✅ 缺节 + 无 `decisions/` 引用 |
| 把 `decisions/` 引用移到**下一小节** | 红（初版用 `grep -A20` 会漏） | ✅ `[FAIL] §判据来源 本节内没有 decisions/ 引用` |

⚠️ **上限的负测试自己也翻车了一次**：初版把上限写成「本节非空行 ≤8」，我据此构造的 8 行输入没变红——**是测试输入选在了边界上，但它暴露了上限定义不忠实**：「每条 ≤3 行」被实现成了总行数，于是「一条写六行」能通过，而那已经是叙事不是校准。改为**逐条计数**后重测四种输入（见上表）。这条本身就是 `gate-design-and-negative-testing §7c` 的实例：阈值必须与它声称约束的对象同源。

**未验证（两条）**：

1. **判据从正文搬走后，判断能力是否下降。** `evals/` 是静态表格，没有 eval harness，所以这件事目前**无法自我验证**。观察点是下一轮执行端/reviewer 是否仍按这些判据行动（例如完成区是否自己贴出比值、整改记录是否自己带 `grep -n` 改后输出）。
2. **`## 校准例` 的上限（≤2 条、≤3 行）是拍的**，不是从数据来的。它的作用是防止该节长成案例库；若将来某个 skill 反复顶到上限，那是重新评估上限的信号，不是加豁免的理由。
