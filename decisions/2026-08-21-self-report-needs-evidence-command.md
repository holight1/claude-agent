# 自述型产出必须带证据命令：整改记录与审查结论一视同仁

**状态**：现行
**日期**：2026-08-21
**触发**：sim SIM-004 架构师终审。DS 对 reviewer 意见的整改记录写「完成区文件清单**撤下** `hierarchy.py`」，实测那一行原封不动还在。同一轮终审还发现，独立 reviewer 声称「实测」的一个数字在交付实现上跑不出来。
**证据**：`~/sim/code-agent/process-notes/0011-review-remediation-record-unverified.md`；`~/sim/tasks/SIM-004-ledger-discriminant-qos-multihop.md` §我核对到不对 2（`grep -n` 实测输出）、§Subagent Review §通过项（`credit 1.467e9 B` 无产生命令）。**本仓不复制其内容，以那些文件为准。**
**作用面**：`collab-framework/DS-common.md` §完成区规范新增「整改记录」小节；`collab-framework/REVIEWER-template.md` 新增「你的数字也必须附产生它的命令」；`skills/task-acceptance-replay/SKILL.md` §跨角色必读、判断程序 §1、诱人错误表；`skills/task-contract-design/SKILL.md` §5；两者 `evals/EVALS.md`。

## 决定

**一 · 整改记录升格为独立小节，每条三段式**：①reviewer 意见原文（可截断）②做了什么 ③**证据命令与输出**。纯文字类整改（改完成区、改文档措辞、撤下清单里的一行）同样要贴 `grep -n` 的**改后**结果。

**二 · 声称「撤下 / 删除 / 改名」的动作，证据必须是「查不到」，不是「我改了」**——`grep -c` 为 0，或 diff 里的删除行。

**三 · 终审对整改记录声称的每个删除动作单独复核。** 整改往往改的是**任务文件本身**、不产生代码 diff，`git show --stat` 看不出来。

**四 · 审查侧与执行侧受同一条数字纪律约束**：写「实测 / 独立复核 / 已复算」时必须贴自己跑的那条命令与输出，不得转述完成区的数字；跑不了就写「未实跑，仅读码判断」——这是合法结论，冒充实测不是。

**五 · 任务书的「流程」一行要点名整改的产出格式**，不指望执行端自己去翻 `DS-common`。

## 为什么

**整改这一步在流程图上根本不是一个节点。** 流水线写的是「执行 → 自起 reviewer → 架构师终审」，三个环节各有产出规范与验证机制：

| 环节 | 产出 | 有没有验证机制 |
|---|---|---|
| 执行 | 完成区 + 测试 | ✅ 测试实跑、数字附命令 |
| reviewer | 审查区 | ✅ 架构师终审会复核 |
| **对 reviewer 意见的整改** | **一段散文自述** | ❌ **无** |

它是附在完成区末尾的一段话，于是继承了完成区自审的全部弱点，却没继承「数字必须带命令」的纪律：整改前后没有第二次 review（reviewer 已交付退出），任务书对整改没有任何格式要求，而终审的注意力天然落在验收表上——整改记录排在验收表**之后**，读起来像收尾说明而不是待核对项。

**这不是不诚实。** DS 把「我决定撤下它」写成了「已撤下」；同一条记录的另一项（改必填）是真做了的，diff 可证。**在只需要动一行文字的动作上，决定与执行之间的距离短到人会以为自己已经做了。** 正因为不是敷衍，所以必须逐条附证据——不能因为抽到一条是真的就放过整段。

**第四条为什么必须加上（用户明确定调「加纪律」）。** 审查区写「反例证伪全部实测红：无钳位 credit **1.467e9 B**」，那个数在交付实现上跑不出来。更关键的是同一份审查**专门核了量纲**并判一致（「`B/s × s` = 字节」），而它的「s」取自测试里的注释 `# 秒`，实现签名是 `dt_ps`。⇒ **查了，而且查出一个自洽的错误。** 数字没有产生它的命令，就无法区分「你跑的」和「你抄的」——而这次两者的差别是 12 个数量级。

**为什么不靠「终审逐条 grep」了事。** sim 本仓 `CLAUDE.md` 已有一条正对着它的规矩——「『结论正确』与『文件等于该结论』是两件事，终审必须分别验」——**它确实拦住了这次**。但它把负担全放在终审那一侧：规矩管的是「谁来发现」，不管「怎么不发生」。下一次终审注意力落在别处时，同样的落空会照原样通过。⇒ 必须同时在产出侧立格式要求。

## 备选方案

- **要求整改后重新起一轮 reviewer**。放弃：整改常常只有一两行，重起一个 subagent 的成本（读任务、读代码、写审查区）远超整改本身，且 reviewer 的第二轮会重复复核已通过的 11 项。折中就是本记录的选择——**不加节点，加证据格式**。
- **把整改记录挪到验收表之前**，靠位置换取注意力。放弃：位置能改一次注意力分配，改不了「自述无需证据」这个根本缺陷；而且验收表在前是对的，整改本来就晚于验收发生。
- **只立整改记录格式，不动审查侧纪律**（即不采纳第四条）。**用户明确定调「加纪律」后放弃**。原本的顾虑是成本：要求 reviewer 逐个数字附命令会让审查变长。但本次事故给了硬证据——审查侧的一个数字既跑不出来、又通过了一次专门的量纲核对——⇒ 审查侧的自述和执行侧的自述是同一个问题，只立一半等于承认另一半可以不带证据。成本用「跑不了就写『未实跑，仅读码判断』」这条出口对冲，不逼它假装跑过。
- **写一个脚本自动校验整改记录里的 `grep` 声称**。**暂不做**：整改声称的对象是任意自然语言（撤下某行、改某措辞），把它变成机器可判的形式需要结构化标记，而结构化标记本身会被填成走过场。当前由终审逐条查的成本可接受。若整改落空第二次出现，按 `gate-design-and-negative-testing §2`（同类缺口第二次换位置即改判别式）重新评估。
